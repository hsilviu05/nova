# Development

## Requirements

| Tool | Version | Notes |
|---|---|---|
| Docker + Compose | recent | The only requirement for the container path |
| Python | 3.12+ | For running the API or tests on the host |
| PostgreSQL | 16+ with pgvector | Provided by Compose; needed locally otherwise |
| Redis | 7+ | Provided by Compose |

## Setup

```bash
cp .env.example .env
echo "NOVA_JWT__SECRET_KEY=$(openssl rand -base64 48 | tr -d '\n')" >> .env
```

The `tr` is not optional: `openssl` wraps base64 at 64 characters, and a value
split across two lines breaks `.env` parsing.

### Everything in containers

```bash
docker compose up --build
```

Postgres and Redis come up first; the API waits for both health checks, runs
`alembic upgrade head`, then binds port 8000.

```bash
curl http://localhost:8000/health
curl http://localhost:8000/ready
open http://localhost:8000/docs
```

### API on the host, dependencies in containers

Faster reload loop.

```bash
docker compose up -d postgres redis

cd services/api
python3.12 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"

alembic upgrade head
uvicorn nova.main:create_app --factory --reload
```

`.env` sets `NOVA_DATABASE__HOST=localhost`, which is what the host path
needs. Compose overrides it to `postgres` for the containerised API.

> The API is served through uvicorn's `--factory` mode. `nova.main` builds
> nothing at import time, so importing it never demands configuration — that
> is what lets the test suite construct an app against a test database.

## Configuration

Environment variables use the `NOVA_` prefix and `__` for nesting:
`NOVA_DATABASE__HOST` → `Settings.database.host`. Everything is typed and
validated at startup. See `.env.example` for the full set.

`NOVA_JWT__SECRET_KEY` is required and must be at least 32 characters. There
is no default, by design.

## Migrations

```bash
cd services/api

alembic upgrade head            # apply
alembic downgrade -1            # roll back one
alembic current                 # what is applied
alembic history                 # all revisions

alembic revision --autogenerate -m "add device table"
alembic check                   # fail if models drift from migrations
```

**Always read an autogenerated migration before committing it.** Autogenerate
detects added and removed objects well; it does not understand renames,
data migrations, or anything requiring a backfill.

`alembic check` runs in CI. A model change without a matching migration fails
the build rather than drifting silently.

### The pgvector extension

The first migration runs `CREATE EXTENSION IF NOT EXISTS vector`, which needs
a privileged role. The Compose image's `POSTGRES_USER` is a superuser, so this
works out of the box. On managed Postgres the owner role usually has the right
(`rds_superuser` on RDS, `cloudsqlsuperuser` on Cloud SQL).

If your role is unprivileged, have an administrator run it once, then apply
migrations normally — the `IF NOT EXISTS` makes it a no-op:

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

## Testing

```bash
cd services/api

pytest                                       # everything
pytest tests/unit                            # no database needed
pytest -m integration                        # database-backed
pytest --cov=nova --cov-report=term-missing
pytest -k reuse -vv                          # one behaviour
```

Tests run against a **real** PostgreSQL and Redis. The mechanisms most worth
testing — the unique index behind reuse detection, `ON DELETE CASCADE`,
partial indexes, `INET` columns — do not exist in SQLite, so a SQLite suite
would pass while production failed.

Create the test database once:

```bash
createdb -h localhost -U nova nova_test
```

Override the target with `NOVA_TEST_DATABASE__*` and `NOVA_TEST_REDIS__*` if
needed. Redis database 15 is used and flushed around every test.

Each test runs inside a transaction that is rolled back afterwards, so tests
neither see nor leave each other's rows and the suite can be run repeatedly
without cleanup.

### Coverage and greenlets

`pyproject.toml` sets `concurrency = ["greenlet", "thread"]`. SQLAlchemy's
asyncio layer resumes coroutines inside greenlets, and without that setting
every line after the first `await` on a repository call is reported
unexecuted — which understated the auth service by roughly half. If coverage
numbers ever look implausibly low for async code, check that setting first.

## Code quality

```bash
cd services/api

ruff check .              # lint
ruff check --fix .        # autofix
ruff format .             # format
mypy                      # strict type check
```

All three run in CI and must pass. `mypy` is configured `strict = true`.

Prefer a narrow `# noqa: RULE` with a comment explaining why over disabling a
rule globally.

## Troubleshooting

**`ValidationError: jwt Field required` at startup**
`NOVA_JWT__SECRET_KEY` is unset. This is intentional — there is no insecure
default. Generate one as shown in Setup.

**`JWT secret_key must be at least 32 characters`**
Likely a truncated value. If you generated it without `tr -d '\n'`, the
newline broke `.env` parsing.

**`connection refused` on port 5432**
Postgres is not up yet, or a local Postgres is already bound to the port. Set
`NOVA_POSTGRES_PORT` to something free.

**`extension "vector" is not available`**
The image is plain `postgres`, not `pgvector/pgvector`. Compose specifies the
right one; a pre-existing volume from the wrong image needs
`docker compose down -v`.

**`got Future attached to a different loop` in tests**
Fixture and test event-loop scopes disagree. Both are set to `session` in
`pyproject.toml`; the session-scoped engine and Redis client hold connections
bound to the loop that created them.

**`Status code 204 must not have a response body`**
FastAPI infers `response_model` from the return annotation, and `-> None`
yields `NoneType`, which is a truthy class. Pass `response_model=None`
explicitly on 204 routes.

## Project layout

```
services/api/
├── src/nova/
│   ├── api/            routes and dependency wiring
│   ├── core/           config, logging, errors, security, clock
│   ├── db/             engine, session, Redis, declarative base
│   ├── middleware/     request context, error handlers
│   ├── models/         SQLAlchemy models
│   ├── repositories/   data access
│   ├── schemas/        Pydantic request/response models
│   ├── services/       business logic
│   └── main.py         application factory
├── alembic/            migrations
└── tests/
    ├── unit/           no database
    └── integration/    database-backed
```

Where new code goes:

- A new endpoint → `api/v1/`, thin, calling one service
- A business rule → `services/`
- A query → `repositories/`
- A table → `models/` plus a migration
- A request or response shape → `schemas/`
